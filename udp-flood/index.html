UDP Flood

& Port Exhaustion
Intinya

UDP Flood adalah serangan yang membanjiri server dengan paket UDP palsu ke nomor port acak. Server sibuk memeriksa setiap port dan membalas "tidak ada aplikasi di sini", sampai tidak sanggup lagi melayani pengguna asli [1].

01

Definisi

UDP Flood adalah serangan volumetrik: tujuannya bukan mencuri data, melainkan menenggelamkan layanan dalam paket sampai tidak bisa dipakai.

UDP (User Datagram Protocol) adalah aturan pengiriman data yang ringan: data langsung dikirim tanpa "berkenalan" dulu dan tanpa jaminan sampai [4]. Port adalah nomor "pintu" layanan di sebuah komputer, dari 1 sampai 65535 [3]. Penyerang menembakkan paket UDP berukuran besar ke port-port acak itu. Untuk setiap paket, server memeriksa apakah ada aplikasi yang menunggu di port tersebut. Karena hampir selalu kosong, server membalas dengan pesan ICMP Destination Unreachable, pesan kendali yang berarti "tujuan tidak dapat dijangkau" [1][5].

Port Exhaustion menggambarkan akibatnya: seluruh rentang port dibanjiri, sehingga kemampuan server untuk memeriksa dan membalas di port-portnya habis. Yang habis adalah tenaga dan jalur internet server, bukan port-nya yang rusak.

02

Tujuan mempelajari

  • Memahami mekanisme mengapa protokol tanpa handshake bisa dipakai untuk melumpuhkan server.
  • Membedakan kapan server tumbang karena jalur internetnya penuh dan kapan karena CPU-nya kehabisan tenaga, karena penangkalnya berbeda.
  • Mengenali tanda-tanda serangan di pusat pemantauan keamanan, sehingga bisa bertindak cepat.
  • Memilih pertahanan yang tepat, dan tahu mengapa sebagian solusi yang terdengar masuk akal ternyata tidak efektif.
03

Relevansi keamanan siber

Keamanan informasi punya tiga pilar, yang disebut CIA Triad: kerahasiaan (confidentiality), keutuhan (integrity), dan ketersediaan (availability). UDP Flood menyerang pilar ketiga: layanan tidak bisa dipakai oleh pengguna sah [1].

  • Kerugian bisnis. Transaksi e-commerce dan pembayaran berhenti, ada penalti SLA (perjanjian jaminan ketersediaan layanan), dan biaya darurat jasa mitigasi [1].
  • Tabir asap. DDoS bisa dipakai untuk mengalihkan perhatian tim keamanan sementara penyerang mencuri data di tempat lain [1][9].
  • Mudah dilakukan. Perangkat IoT yang tidak aman dan server publik yang salah konfigurasi membuat banjir raksasa bisa dibuat dengan modal kecil [8][10].
04

Etika

Simulator di situs ini hanya model visual dengan angka buatan; tidak ada trafik jaringan sungguhan. Teknik serangan hanya boleh dipelajari dan diuji di lab yang diizinkan, misalnya mesin latihan yang Anda jalankan sendiri [3]. Mengakses atau mengganggu sistem elektronik orang lain tanpa hak adalah tindak pidana menurut UU ITE [12][13].

Yang perlu diingat

  1. UDP Flood membanjiri port acak 1–65535 dengan paket UDP palsu berukuran besar.
  2. Server memeriksa port, tidak menemukan aplikasi, lalu membalas ICMP Destination Unreachable.
  3. Siklus itu menguras server sampai tidak responsif; yang diserang adalah ketersediaan.
  4. Pelajari hanya di lab yang diizinkan.

Cara kerjanya

Intinya

UDP tidak punya proses kenalan, jadi server harus memproses setiap paket yang datang. Botnet, alamat palsu, dan amplifikasi membuat jumlah paket itu jauh melebihi kemampuan server.

01

Mengapa UDP rentan

UDP bersifat connectionless (tidak membangun sambungan lebih dulu) dan tidak memiliki otentikasi handshake [1]. Standarnya sendiri menyebut UDP sebagai mekanisme minimal yang tidak menjamin pengiriman maupun perlindungan duplikasi [4]. Bandingkan dengan TCP, yang wajib berkenalan tiga langkah:

TCP · kenalan dulu

Server baru melayani setelah ada balasan yang membuktikan pengirimnya ada [1].

UDP · langsung kirim

Tidak ada salam dan tidak ada pemeriksaan pengirim. Setiap paket wajib diproses [4].

Salah kaprah: "UDP itu protokol yang buruk." Tidak. UDP sengaja dibuat ringan dan sangat berguna untuk DNS (port 53), NTP (123), SNMP (161), atau panggilan video [3]. Masalahnya ada pada tidak adanya pemeriksaan pengirim, yang dimanfaatkan penyerang.

02

Komponen & teknologi

Paket UDP buatan

Paket berukuran besar yang isinya tidak berguna, dikirim ke port acak 1–65535 [1].

Port dan kernel server

Sistem operasi memeriksa apakah ada program yang "mendengarkan" di port tujuan. Pemeriksaan ini terjadi untuk setiap paket [7].

ICMP Destination Unreachable

Pesan ICMP tipe 3; kode 3 berarti port unreachable, dikirim host saat tidak ada aplikasi di port itu [5].

Bandwidth

Lebar "pipa" koneksi internet, diukur dalam Gbps (gigabit per detik) atau Tbps. Serangan volumetrik berusaha memenuhinya [1].

Botnet dan C2

Botnet adalah ribuan perangkat terinfeksi yang dikendalikan dari jauh. Botmaster memberi perintah lewat server C2 (Command & Control) berbasis HTTP, IRC, atau P2P kepada pasukan zombie [1].

IP spoofing

Memalsukan kolom alamat pengirim di kepala paket, untuk menyembunyikan identitas atau mengarahkan balasan ke korban [2].

03

Refleksi & amplifikasi

Refleksi: penyerang tidak mengirim paket langsung ke korban. Ia mengirim permintaan ke server publik (reflector) dengan alamat pengirim dipalsukan menjadi alamat korban [1]. Amplifikasi: permintaannya kecil, tetapi balasannya raksasa. Dengan cara ini, bandwidth penyerang sebesar 10 Mbps bisa menjadi banjir 500 Mbps ke korban [1].

LayananCara disalahgunakanFaktor (materi kuliah)BAF menurut CISA
DNS · UDP 53Query ANY/TXT dengan EDNS0 ke resolver terbuka: ±60–64 byte menjadi 3.000+ byte [1]±50×28–54×
NTP · UDP 123Perintah monlist mengembalikan daftar 600 IP terakhir yang menghubungi server [1]±200×556,9×
Memcached · UDP 11211Server cache publik membalas berukuran megabyte dari permintaan beberapa byte [1]hingga 50.000×10.000–51.000×

BAF (Bandwidth Amplification Factor) adalah perbandingan ukuran balasan terhadap ukuran permintaan. Angkanya berbeda antarsumber karena bergantung pada konfigurasi server dan cara pengukuran; simulator di situs ini memakai angka materi kuliah [1][8].

04

Contoh kasus: Mirai

Mirai mengubah kamera IP dan router rumahan menjadi pasukan DDoS.

Mirai memindai alamat IP publik di port Telnet (23 dan 2323) dan mencoba kamus berisi 60 kombinasi password bawaan pabrik. Perangkat IoT yang tidak pernah diganti password-nya langsung terinfeksi dan menjadi "tentara" DDoS [1]. Studi retrospektif tujuh bulan yang dipresentasikan di USENIX Security 2017 mencatat pertumbuhan Mirai hingga puncak sekitar 600 ribu infeksi [10].

Botnet modern juga memakai DGA (Domain Generation Algorithm): ribuan nama domain C2 dibuat acak setiap hari berdasarkan tanggal sistem, sehingga pusat kendalinya sulit dimatikan [1].

Pelajaran. Ganti password bawaan router, kamera CCTV, dan perangkat pintar. Perangkat dengan password pabrik adalah bahan baku botnet.

05

Ancaman terkait

Serangan DoS terbagi dua keluarga. Bandwidth Saturation menjenuhkan pipa data; contohnya ICMP Flood, UDP Flood, dan DNS Amplification. Resource Exhaustion menguras RAM dan CPU dengan cara yang lebih "cerdik", misalnya SYN Flood dan Slowloris [1].

SeranganLayerCara kerjaYang dihabiskanSatuan

ICMP Flood3Banjir ICMP Echo Request besar; server dipaksa membalas Echo ReplyBandwidth, CPUGbps / Tbps
Smurf3Ping ke alamat broadcast dengan IP korban dipalsukan; semua host membalas ke korbanBandwidth korbanGbps
SYN Flood4Ribuan SYN palsu; antrean koneksi setengah terbuka penuhRAM tabel koneksiPaket/detik

Sumber tabel: [1]. Sebagai pembanding, CISA mendaftar gejala umum DoS: jaringan sangat lambat, situs tertentu tidak bisa diakses, atau tidak bisa mengakses situs apa pun [9].

Yang perlu diingat

  1. UDP connectionless dan tanpa handshake, sehingga server tidak bisa menolak paket sebelum memprosesnya.
  2. Trafik datang dari botnet seperti Mirai, sering dengan alamat pengirim palsu.
  3. Amplifikasi melipatgandakan banjir: DNS ±50×, NTP ±200×, Memcached hingga 50.000×.
  4. UDP Flood termasuk Bandwidth Saturation, diukur dalam Gbps atau Tbps.

Dari bot sampai server tumbang

Intinya

Serangan berjalan dalam tujuh tahap, dari merekrut perangkat zombie sampai server tidak responsif. Pembela punya kesempatan mendeteksi di tahap-tahap akhir.

7 tahapserangan, lalu deteksi oleh pembela
01

Alur serangan

Diagram ringkas dari kiri ke kanan.

Geser diagram ke samping untuk melihat seluruhnya.

02

Tahap demi tahap

  1. Merekrut pasukan.Perangkat IoT dengan password bawaan diinfeksi dan bergabung ke botnet, seperti cara kerja Mirai [1][10].
  2. Menyiapkan penyamaran.Alamat pengirim dipalsukan (IP spoofing), atau dipilih server publik yang bisa memantulkan balasan besar (reflector) [1][2].
  3. Perintah dilepaskan lewat C2.Botmaster memerintahkan semua bot menyerang serentak [1].
  4. Banjir ke port acak.Paket UDP buatan berukuran besar ditembakkan ke port acak 1–65535 milik korban [1].
  5. Server memeriksa port.Untuk setiap paket, server mencari aplikasi yang mendengarkan di port tujuan [1][7].
  6. Balasan ICMP Destination Unreachable.Karena tidak ada aplikasi aktif, server membuat dan mengirim balasan "port unreachable" untuk setiap paket [1][5].
  7. Jenuh dan tumbang.Siklus periksa-dan-balas menguras sistem, atau pipa internet penuh lebih dulu. Server menjadi tidak responsif bagi pengguna asli [1].
03

Sisi pembela: deteksi

Tim pemantau keamanan (SOC, Security Operations Center) mencari tiga indikator: lonjakan CPU di atas 95%, lonjakan PPS (paket per detik) atau RPS (permintaan per detik) yang tidak wajar, dan dominasi jawaban HTTP 503 "Service Unavailable" [1]. Khusus UDP Flood, tandanya juga berupa paket UDP masuk ke banyak port berbeda dan lonjakan ICMP Destination Unreachable keluar.

Terminal Linux · deteksi (hanya membaca)
# Hitung koneksi SYN_RECV yang menggantung
netstat -an | grep SYN_RECV | wc -l
netstat -an menampilkan semua koneksi, grep menyaring yang setengah terbuka, wc -l menghitungnya. Lebih dari 100 adalah indikasi awal SYN Flood [1].
# Alamat IP dengan koneksi terbanyak
netstat -ntu | awk '{print $5}' | cut -d: -f1 | \
sort | uniq -c | sort -n
Ambil kolom alamat lawan, buang nomor port, lalu hitung kemunculan tiap IP. Angka terbesar ada di paling bawah [1].

Catatan jujur. UDP tidak punya "koneksi", jadi daftar netstat tidak banyak membantu untuk UDP Flood, dan pada serangan dengan alamat palsu, IP yang terlihat bukan pelaku sebenarnya. Untuk UDP Flood, pantau grafik PPS, bandwidth, dan CPU.

Yang perlu diingat

  1. Rekrut bot, siapkan penyamaran, perintah lewat C2, banjiri port acak.
  2. Server memeriksa port lalu membalas ICMP untuk setiap paket.
  3. Server tumbang karena CPU habis, pipa penuh, atau keduanya.
  4. Deteksi lewat CPU > 95%, lonjakan PPS/RPS, dan banyak HTTP 503.

i

Cara model menghitung

  • Trafik serangan = jumlah bot × paket per detik × ukuran paket. Untuk amplifikasi, ukuran yang sampai ke korban = ukuran permintaan × faktor (DNS 50×, NTP 200×, Memcached 50.000×) [1].
  • Pipa: jika total trafik melebihi bandwidth server, paket dibuang secara proporsional, termasuk paket pengguna asli.
  • CPU: setiap paket yang lolos butuh 1 unit kerja untuk memeriksa port, ditambah 1 unit jika port kosong karena harus membuat balasan ICMP. Permintaan pengguna asli butuh 3 unit.
  • Pengguna asli: terdapat 20.000 permintaan per detik berukuran 600 byte. Persentase yang terlayani turun jika pipa penuh atau CPU melebihi 100%.
  • Asumsi pertahanan: scrubbing membuang 99% trafik serangan di hulu; BCP 38/uRPF diasumsikan diterapkan 75% jaringan sumber; rate limit ICMP membatasi balasan menjadi 1.000 per detik; firewall lokal sanggup memblokir hingga 200 alamat IP.

Angka-angka ini disederhanakan agar perbedaan antarskenario terlihat jelas, bukan untuk meramalkan kondisi jaringan sungguhan.

Menahan banjir

Intinya

Banjir volumetrik harus disaring sebelum mencapai pipa korban. Pertahanan di server sendiri hanya membantu jika pipanya belum penuh.

Di halaman ini

  1. Mencegah
  2. Memperbaiki kerentanan
  3. Praktik yang disarankan
  4. Mengapa blokir IP lokal gagal
01

Mencegah

Scrubbing di hulu (BGP Anycast)

Trafik dibelokkan ke pusat pembersihan cloud berkapasitas besar. Dengan Anycast, satu alamat IP diumumkan dari banyak pusat data sehingga banjir terpecah ke lokasi terdekat [1][14]. Inilah solusi utama untuk banjir Gbps–Tbps.

BCP 38 / uRPF

Penyedia internet menyaring paket keluar yang alamat pengirimnya bukan milik jaringannya, sehingga paket palsu dibuang di sumber [2][6]. NIST juga merekomendasikan validasi alamat sumber dengan ACL dan uRPF [11].

Rate limiting balasan ICMP

Kebanyakan sistem operasi membatasi laju balasan ICMP agar tidak ikut menguras sumber daya saat diserang [7]. Ini membantu CPU, tetapi tidak membebaskan pipa yang sudah penuh.

Layanan perlindungan DoS

CISA menyarankan berlangganan layanan yang mendeteksi aliran trafik abnormal dan mengalihkannya dari jaringan Anda [9].

02

Memperbaiki kerentanan

  • Jangan menjadi reflector. Matikan akses publik ke monlist NTP, tutup UDP 11211 Memcached dari internet, dan jangan membuka resolver DNS untuk umum [1][8]. Pada konfigurasi NTP umum, monlist dimatikan dengan menambahkan pembatasan noquery.
  • Matikan layanan yang tidak dipakai agar permukaan serangan mengecil [1].
  • Ganti password bawaan perangkat IoT agar tidak direkrut botnet seperti Mirai [1][10].
03

Praktik yang disarankan

  1. Kenali kondisi normal.Catat PPS, bandwidth, dan CPU harian agar lonjakan mudah dikenali.
  2. Pantau indikator SOC.CPU di atas 95%, lonjakan PPS/RPS, dan banyak HTTP 503 [1].
  3. Siapkan rencana darurat.Kontak ISP dan penyedia mitigasi, plus rencana pemulihan bencana [9].
  4. Waspadai tabir asap.Saat menangani DDoS, tetap pantau sistem lain untuk penyusupan senyap [1][9].
04

Mengapa blokir IP lokal gagal

  1. Pipa sudah penuh lebih dulu.Firewall lokal berada di ujung pipa. Banjir Gbps memenuhi jalur dari ISP sebelum firewall sempat memilah, jadi pengguna asli tetap tidak bisa lewat [1][7].
  2. Alamatnya palsu atau sah.Pada spoofing, IP berganti acak. Pada amplifikasi, paket datang dari server publik yang sah [2].
  3. Terlalu banyak sumber.Botnet bisa berisi ratusan ribu perangkat [10].

Pengecualian kecil: untuk botnet sangat kecil tanpa pemalsuan dan pipa yang masih longgar, blokir IP bisa meringankan CPU. Coba buktikan di simulator.

Yang perlu diingat

  1. Saring di hulu dengan scrubbing dan Anycast; itu satu-satunya cara menahan banjir Tbps.
  2. BCP 38/uRPF membuang paket palsu di sumbernya.
  3. Rate limit ICMP membantu CPU, bukan pipa.
  4. Jangan biarkan server Anda menjadi reflector, dan ganti password bawaan IoT.
  5. Blokir IP di firewall lokal tidak efektif untuk serangan volumetrik.
